# 性能报告：Transformer 自注意力加速（gpu-attention-demo）

> 与自动生成的 `results.md`（每次运行程序都会覆盖）不同，本文件是**人工整理的分析报告**，
> 汇总各方案实测性能并解释「收益从何而来」。原始数据以 `results.md` 为准。

## 1. 测试对象与环境

| 项目 | 内容 |
|---|---|
| 计算载体 | 单样本、单头自注意力 `O = softmax(Q·Kᵀ / √d) · V` |
| 计算热点 | 两次 GEMM：`QKᵀ`（N×N×d）与 `PV`（N×d×N），占绝大部分 FLOP |
| 测试规模 | `d = 64`，`N ∈ {1024, 2048, 4096}` |
| GPU | NVIDIA RTX 3080 Laptop（Ampere, CC 8.6, 16GB），编译目标 `-arch=sm_86` |
| 工具链 | CUDA 13.0 (nvcc)，零第三方性能库 |
| 正确性容差 | FP32 路径 1e-3，FP16 路径 1e-2 |

### 数据口径（读表前必看）

- **kernel 时间**：CUDA event 测得的纯 GPU 计算时间，**不含** H2D / D2H 传输 —— 这是观察「优化阶梯」最干净的指标，下文分析主要用它。
- **e2e 时间**：从调用到结果回主机的完整耗时，含内存分配、数据拷贝、（L5 的）FP16 转换等。
- **加速比**：程序采用 `CPU 串行 e2e ÷ 该层 kernel 时间`。这个口径**对 GPU 有利**（未计入传输），且 CPU 基线是朴素三重循环实现（无 SIMD、无分块、无多线程），因此**绝对数字偏大，不宜直接引用给学生做「GPU 有多快」的论据**。
- **真正公平的对比是 GPU 各层之间的相对增益**（第 3 节的「对 L2 增益」列）。

## 3. 逐层收益分析

### L1 → L2：并行化本身（最猛烈的一击）

**做了什么**：把「每个输出元素一次点积」从单线程循环，铺成 N² 个 CUDA 线程，每线程算一个元素。

**为什么有效**：自注意力的每个输出元素之间**完全独立**，是教科书级的 embarrassingly parallel。RTX 3080 Laptop 有数千个 FP32 核心、可同时驻留数万个线程，把串行工作量铺开后获得了**数百倍**（N=4096）到**上千倍**（N=1024）的加速。

**为什么没到理论峰值**：朴素 kernel 的算术强度极低 —— 每算一个输出元素要从全局内存读 2d 个 float（Q 一行 + K 一行），即约 `d / (2d × 4B) = 1/8 FLOP/Byte`，远低于 Ampere 饱和算力所需的水平。所以 L2 **卡在内存带宽上**，几千个核心大部分时间在等数据。这正是后续 L3/L4 要解决的问题。

> 补充提醒：CPU 基线是刻意朴素的实现（三重循环 + 转置访问导致的 cache 抖动）。若用 OpenMP + SIMD + 分块重写 CPU 版本，其耗时会大幅下降，加速比也会相应缩小 —— 课堂上若要严谨，建议明确这一点。

### L2 → L3：共享内存分块（提算术强度）

**做了什么**：把 Q、K 切成 16×16 的 tile 载入 `__shared__`，一个 tile 的数据被块内线程复用于多个输出元素。

**为什么有效**：朴素版每个输出元素都重新读一遍 Q/K 的行，全局读总量约 `2·N²·d`；分块后同一 tile 只从全局读一次，全局读量降到约 1/16（tile 边长之比），同时访存形态变为**合并访存**（coalesced），带宽利用率大幅提升。

**实测为什么只有 1.0x～1.7x，而不是十几倍？**

- `d = 64` 很小，Q/K/V 的总数据量在 N=2048 时仅约 1.5 MB，**能被 GPU 的 L2 cache（数 MB 量级）大部分吸收** —— 硬件已经「顺手」完成了复用，手写 shared memory 只是把 L2 的活搬到 SMEM，收益被抵消。
- N=2048 上出现 **1.00x（几乎无提升）** 正是这个原因的最佳例证；到 N=4096 数据量涨到约 3 MB、L2 开始吃不消时，分块价值才显现（1.69x）。
- 分块自身也有成本：`__syncthreads()` 同步、tile 载入代码、寄存器与 SMEM 占用上升（影响 occupancy）。

**教学价值**：这一层是「roofline 模型」的活教材 —— **优化访存能拿多少收益，取决于你原本离带宽墙有多远**。

### L3 → L4：向量化 + 消 bank conflict + 循环展开（榨干带宽与指令）

**做了什么**：

1. `float4` 向量化加载：一个线程一次读 4 个 float（16 B），访存指令数降为 1/4，且 128-bit 事务是合并访存的最优形态（一个 warp 32 线程 × 16 B = 512 B，正好 4 条 128 B cache line，零浪费）。
2. padding 消除 bank conflict：shared memory 有 32 个 bank；16×16 的 float tile 按行主序存放时，按列访问会产生多路 bank 冲突。把行宽从 16 pad 到 17（奇数跨度）后，冲突消除。
3. 循环展开：减少循环分支与地址计算指令，提升指令级并行（ILP），让访存与计算更好重叠。

**实测：N=1024 → 1.22x，N=2048 → 1.89x，N=4096 → 3.40x。**

**为什么收益随规模单调增长**：规模越大，kernel 越靠近「带宽/指令发射」瓶颈，而这三项优化**恰恰全部作用在带宽与指令流上**，因此价值被放大；小规模时 kernel 还没被瓶颈卡住，优化自然无从体现。

> 这一层是本 demo 中**性价比最高**的手写优化（N=4096 上 3.4x，且不依赖专用硬件、可移植到任何 GPU）。

### L4 → L5：Tensor Core（专用硬件的又一个量级）

**做了什么**：用 WMMA API 把两个 GEMM 改写成 16×16×16 的 FP16 矩阵乘累加（`mma.sync`），保留 FP32 累加以控制精度损失。

**为什么有效**：Tensor Core 是专用的矩阵乘数据通路，一条指令完成 64 个 FMA 的等效工作量，其等效吞吐为通用 FP32 CUDA core 的**数倍**（具体倍数随架构与型号而异，Ampere 消费级上约 4～8 倍量级）。GEMM 的语义与它完全匹配，因此能直接吃满这条通路。

**实测：N=1024 → 1.84x，N=2048 → 2.27x，N=4096 → 2.39x（对 L4）；对 L2 则达 3.21x / 4.30x / 13.70x。**

**为什么不是理论上的数倍？四个原因都很有教学价值**：

1. **GEMM 太「薄」**：`d = 64` 意味着 K 维只有 64，Tensor Core 流水线的填充/排空开销占比很大，无法持续满载。
2. **FP16 转换有固定成本**：需要先把数据转成 FP16 并额外拷贝。这在小规模时甚至会**吞掉全部收益** —— N=1024 上 L5 的 kernel（0.110 ms）比 L4（0.203 ms）快，但 **e2e 反而从 3.54 ms 退化到 6.99 ms**，就是转换与拷贝开销所致。
3. **Amdahl 定律**：只有两个 GEMM 走 Tensor Core，softmax、缩放、逐元素操作仍在 CUDA core 上，这部分时间无法被加速。
4. **带宽天花板**：N=4096 时中间激活有 N² = 1678 万个元素，几个张量的读写合计已达数百 MB，逼近显存带宽上限，算力再强也得等数据。

**结论**：**专用硬件的收益是规模的函数**。规模不足时固定开销吃掉收益 —— 这是「为什么小模型上 FP16 不一定更快」的直接答案。

## 4. 与 cuBLAS 的对照

| 规模 | 手写最优 (L5) | cuBLAS FP32 | cuBLAS FP16 |
|---|---|---|---|
| N=1024 | 0.110 ms | 0.134 ms | 0.282 ms |
| N=2048 | 0.305 ms | 0.467 ms | 0.390 ms |
| N=4096 | **1.847 ms** | 1.343 ms（快 1.38x） | **1.846 ms（与 L5 持平）** |

**怎么解读**：

- **N=4096 上，手写 L5（1.847 ms）与 cuBLAS FP16（1.846 ms）几乎完全相同** —— 说明把底层优化（分块、向量化、Tensor Core）吃透后，手写实现完全可以逼近工业级库。这是本 demo 最有力的结论之一。
- 但 **cuBLAS FP32 在 N=4096 上仍快 1.38x**，且在小/中规模上 e2e 优势明显（N=2048：6.85 ms vs L4 的 9.08 ms）—— 差距来自工业库的**工程积累**：多算法自动选择、kernel 融合、针对不同形状的调优分支、更精细的流水线编排。
- **cuBLAS 仅作对比基线**。本 demo 的 L1–L5 全部手写、零性能库依赖，每个优化点都可见、可讲、可改 —— 这正是教学 demo 与生产库的定位差异。

## 5. 核心结论（可直接用于课堂）

1. **并行是第一生产力**：从串行到朴素 GPU 并行，一步就是数百到上千倍。但这一步的收益里有相当一部分来自「CPU 基线太朴素」，需向学说明白。
2. **并行之后，瓶颈立刻转移到访存**：朴素 kernel 的算术强度只有 1/8 FLOP/Byte，几千个核心在饿着等数据。
3. **优化要量化验证，不能想当然**：共享内存分块在 N=2048 上收益为 **0**（L2 cache 已经把活干了），在 N=4096 上才值 1.69x —— 用数据说话，而不是背「分块一定快」的教条。
4. **微优化（向量化/消冲突/展开）性价比最高**：无需专用硬件，N=4096 上白拿 3.4x。
5. **专用硬件（Tensor Core）需要规模才能变现**：N=1024 上 kernel 快 1.84x 却因转换开销导致端到端变慢；N=4096 上才真正兑现 2.4x，并对朴素版达 13.7x。
6. **手写做到位可以逼近工业库**：N=4096 上与 cuBLAS FP16 打平，差距只剩工程积累部分。
