# 性能报告：光线追踪加速（gpu-raytracer-demo）

> 与自动生成的 `results.md`（每次运行程序都会覆盖）不同，本文件是**人工整理的分析报告**，
> 汇总各方案实测性能并解释「收益从何而来」，另附一组专门设计的**规模扩展性实验**数据。

## 1. 测试对象与环境

| 项目 | 内容 |
|---|---|
| 计算载体 | Whitted 风格光线追踪：逐像素主光线 + 递归反射/折射 + 阴影检测 + Phong 着色 |
| 并行特性 | 每条光线独立 —— 教科书级 embarrassingly parallel，但**同 warp 内光线路径高度发散** |
| 默认场景 | 260 个球（4 参考球 + 256 随机球）、3 个光源、1 个棋盘格地面，1024×1024，深度 5 |
| GPU | NVIDIA RTX 3080 Laptop（Ampere, CC 8.6, 16GB），编译目标 `-arch=sm_86` |
| 工具链 | CUDA 13.0 (nvcc)，零第三方性能库 |
| 正确性判据 | 逐通道 **均值**绝对误差 < 1e-2 **且**像素命中率 > 99%（非 max，理由见第 5 节） |

## 3. 规模扩展性实验：BVH 的价值随球数增长

BVH 是算法复杂度层面的优化（O(N) → O(log N)），其收益**天然依赖问题规模**。默认场景只有 260 个球，远不足以展示它的全部威力。为此专门跑了一组对照实验（256×256，深度 4）：

| 球数 | L3 朴素 (ms) | L4 常量内存 (ms) | L5 深度优化 (ms) | L6 BVH (ms) | **BVH 相对 L3** | BVH 相对 L5 |
|---|---|---|---|---|---|---|
| 132 | 4.38 | 3.69 | 1.95 | 2.27 | 1.93x | 0.86x |
| 260 ※ | 145.064 | 270.533 | 107.957 | 76.981 | 1.88x | 1.40x |
| 516 | 18.95 | 36.47 | 17.78 | 8.58 | **2.21x** | **2.07x** |
| 1028 | 40.45 | 38.11 ⚑ | 30.46 | 12.45 | **3.25x** | **2.45x** |

※ 260 球一行来自默认配置（1024×1024，深度 5），绝对时间不可与其他行直接比较，但**比值具有可比性**。
⚑ 1028 球超出常量内存上限（1024），L4 已自动退回全局内存朴素路径（数值结果与 L3 一致）。

### 复现性说明（重要）

256×256 下 GPU kernel 只有几毫秒到几十毫秒，计时受 GPU 频率与缓存状态影响显著。**同一配置重复运行，132 球一档各层波动可达 10%～110%，516 / 1028 两档波动约 10%～30%。** 因此：

- **132 球一档只能看趋势，不能用于定量结论** —— 例如「L5 是否快于 L3」在不同轮次会得到相反答案（本轮 L5 快 2.25x，另一轮 L5 慢 1.15x）。
- **核心结论由 516 与 1028 两档支撑**，它们在重复测量中稳定得多：BVH 相对朴素版为 **2.21x / 2.54x**（516 球）与 **3.25x / 3.75x**（1028 球）。

**结论（趋势稳定，远超噪声）**：

- **BVH 相对朴素版：约 1.9x → 2.2x → 3.3x**，随球数单调增长。球越多，BVH 赚得越多。
- **BVH 相对 L5：1.40x → 2.07x → 2.45x**，同样单调增长。
- **L5 对 L3 的增益稳定在 1.1x～1.3x**（516 球 1.07x、1028 球 1.33x、260 球 1.34x），因为光线追踪的瓶颈在算力与分支，而非纯带宽。

> 课堂建议：把球数调到 1024 或 2048 再跑一次（`--spheres 1024`），BVH 的优势会显著放大，
> 这是演示「算法复杂度优化」最直观的方式。球数超过 1024 时 L4 会自动退回朴素路径并打印提示，不会中断。

## 4. 逐层收益分析

### L1 → L2：CPU 多核并行（7x～8x）

**做了什么**：`#pragma omp parallel for schedule(dynamic)`，把像素循环分给所有 CPU 线程。

**为什么有效**：像素间零依赖，直接并行；`dynamic` 调度缓解了负载不均（部分像素的递归深度更大、计算更久）。

**为什么只有 7x～8x**：CPU 只有**数十个物理核心**，且受内存带宽（笔记本 DDR 约 50 GB/s）限制。实测 6.7x～8.4x 基本对应物理核心数，属于合理的近线性加速。

### L2 → L3：GPU 朴素并行（对 OpenMP 约 250x，对串行 2113x）

**做了什么**：每个像素一个 CUDA 线程，光线追踪主体从递归改为**迭代栈**（CUDA 上递归的栈开销与调度成本过高，本实现用固定容量 24 的显式栈）。

**为什么有效**：

1. **并行度差三个数量级**：1024×1024 = 100 万个像素 → 100 万个线程。GPU 有数千个 FP32 核心、可驻留数万个线程，远超 CPU 的数十核。
2. **高带宽**：RTX 3080 Laptop 显存带宽约 448 GB/s，是笔记本内存的近 10 倍，喂得上大量并发线程。
3. **硬件多线程隐藏延迟**：光线求交的访存高度不规则，一个 warp 等数据时 SM 立刻切到另一个 warp —— 光线追踪这种「访存随机 + 计算密集」的负载正好受益。
4. 实际光线量远不止 100 万：每次命中会派生反射 + 折射两条子光线，深度 5 意味着单像素最多数十条光线，总量达**数千万条**。

### L3 → L4：`__constant__` 场景 —— 一次失败但有价值的优化（默认配置下**慢 1.87x**）

**原本的设想**：场景数据只读、且被所有线程共享，放进 `__constant__` 可以享受常量缓存的**广播**（broadcast）能力，削减全局内存流量。

**为什么反而慢了（三个叠加原因）**：

1. **访问模式不匹配（主因）**：常量内存的全部优势建立在「同一 warp 的 32 个线程读**同一地址** → 单次广播服务全 warp」之上。但光线追踪里，同一 warp 的 32 条光线会打向不同方向、命中不同的球、在**不同的循环迭代**退出（早退与递归分支）。访问地址一旦发散，常量缓存就必须为每个不同地址**串行服务**，退化成「每线程单独取数」，比走 L1/L2 的全局内存路径更慢。
2. **容量溢出**：常量缓存每 SM 仅 **8 KB**。260 个球 × 约 52 B ≈ 13.5 KB 已超出容量，只能反复驱逐与重取；球数增到 516 时约 27 KB，抖动雪上加霜 —— 这解释了为什么 L4 的劣势**随球数放大**（260 球慢 1.87x → 516 球慢 1.9x～3.2x）。
3. 常量路径使用了独立的 `trace_const` 代码分支，编译器优化程度也不及主路径。

**实测边界**：在 132 球的小场景上，L4 与 L3 的差距**落在测量噪声范围内**（不同轮次结果相反），此时常量数据能装进缓存且总访存量小，劣势尚不明显；球数 ≥260 后 L4 才稳定劣于朴素版。

**教学价值**：这是全项目最有价值的一课 —— **没有银弹，优化手段必须匹配访问模式**。常量内存适合**小尺寸 + uniform 访问**的数据（相机参数、少量光源、小型查找表），绝不适合「大数组 + 发散访问」。一个反例比三个正例更能让学生记住这一点。

### L4 → L5：访存与指令级深度优化（对 L4 约 2.5x，对 L3 约 1.1x～1.3x）

**做了什么**：

1. **`float4` 打包**：把球的 center（12 B）+ radius（4 B）打包成一个 16 B 的 `float4`，一次 128-bit 加载就取回相交测试所需的全部数据 —— 访存指令数降为约 1/4，且 16 B 对齐的连续访问是合并访存的最佳形态。
2. **`__ldg` 只读缓存提示**：标注数据只读后走 read-only 缓存路径，缓存策略更激进、延迟隐藏更好。
3. **`#pragma unroll 4`**：展开求交循环，减少分支与索引计算指令，提升指令级并行。
4. **16 字节合并写**：framebuffer 从 3 次独立 float 写改为 1 次 `float4` 写，写事务数降为 1/3。

**为什么收益不如注意力 demo 的同层（3.4x）**：光线追踪的瓶颈主要落在**算力和分支**上，而非纯带宽，因此「带宽/访存类」优化能被兑现的比例天然更低 —— 实测对 L3 只稳定在 1.1x～1.3x，正是这个原因。

### L5 → L6：BVH 加速结构（1.40x，且随球数增长到 2.4x+）

**做了什么**：CPU 端用中点分割递归建一棵 BVH（叶节点容纳 4 个球），GPU 端用**栈式 AABB 遍历**（`int nstack[32]`）逐层剪枝，不再对每个球做暴力测试。

**为什么有效**：把「每条光线遍历全部 N 个球」的 **O(N)**，变成「沿树下降 + 整棵子树剪枝」的 **O(log N + 实际命中数)**。这是**复杂度级别的改变**，也是它区别于前面所有「常数因子优化」的本质所在 —— 前面各层改的是系数，BVH 改的是增长阶。

**为什么没有达到理论上的数十倍**（1028 球时也只 3.25x～3.75x）：

1. **warp 发散**：同一 warp 的 32 条光线走**不同的树路径**、遍历步数不同，warp 内必须串行走完所有分支路径 —— BVH 的剪枝收益被大幅抵消。这是光线追踪与 GEMM 最本质的区别（GEMM 里同 warp 的线程步调高度一致）。
2. **遍历自身有开销**：AABB 测试、栈操作消耗指令与寄存器，32 层栈占用局部内存，压低 occupancy。
3. **树的质量有限**：本实现用简单的中点分割建树，**未做 SAH（表面积启发式）**优化，剪枝效率不是最优。工业渲染器普遍用 SAH 或线性 BVH。
4. **朴素版有早退**：命中即停，平均测试的球数远小于 N，削弱了 BVH 的相对优势。

**小球数场景为什么会亏**：BVH 有固定成本（AABB 测试、栈 push/pop、分支判断），球少时朴素版循环本身就短，固定成本可能盖过剪枝收益。132 球一档 BVH 相对 L5 为 0.86x（略亏），但**该档噪声极大，仅作参考**。

**结论**：**算法复杂度优化的收益是问题规模的函数**。260 球的场景对 BVH 而言太小儿科；真实渲染器面对的是百万级图元，那时 BVH 带来的是数量级差距。这正是「复杂度分析在工程上意味着什么」的最佳演示 —— 而本 demo 的扩展性实验让学生可以亲手把球数加上去、看着优势曲线抬起来。

## 5. 正确性度量说明

- 报告中的 **max 误差 6.4e-01** 看起来很大，但 **mean 误差只有 1.05e-05、命中率 99.98%** —— 百万像素中只有极少数**擦边光线**在 CPU / GPU 上走了不同分支（命中球面 vs 命中背景，色差可达 0.5+），这是浮点精度与逐像素独立判断的**固有发散**，不是 bug。
- 因此本 demo 采用 **mean + 命中率**双判据（mean < 1e-2 且命中率 > 99%），同时保留 max 供参考。
- 小场景（132 球）下 max 仅 1.06e-02、命中率 100%，印证了「擦边光线越少、发散越少」。

## 6. 实现限制与注意事项

- **L4 常量内存上限 1024 个球**：超出时会打印 `[WARN]` 并**自动退回全局内存朴素路径**（数值结果与 L3 一致），不会中断测试。（早期版本在超限时因拷贝越界而报错中止，已修复。）
- 反射/折射深度上限 10（迭代栈容量保护）。
- **小规模场景的计时噪声**：kernel 时间低于 ~10 ms 时重复运行可差 10%～110%，做定量对比请提高分辨率或球数。
- 本机 PPM 输出（`ref.ppm` / `out.ppm`）已被 `.gitignore` 排除，不进仓库。

## 7. 与注意力 demo 的核心对照

| | 注意力 demo | 光线追踪 demo |
|---|---|---|
| 负载语义 | 矩阵乘（GEMM） | 无矩阵语义，逐光线树遍历 |
| 同 warp 访问模式 | 高度一致（分块内协同） | 高度发散（各走各的） |
| 终极优化 | **Tensor Core**（专用硬件） | **BVH**（算法级复杂度优化） |
| 常量内存优化 | 未采用 | **失败案例**（慢 1.87x） |
| 瓶颈 | 带宽 → 算力 | 算力 → 分支与发散 |
| 优化收益来源 | 主要靠榨带宽与专用硬件 | 主要靠改变算法复杂度 |

**一句话总结**：**不是所有负载都能用同一种硬件加速，优化手段必须贴合负载特征。** 同为 GPU 并行程序，一个靠专用矩阵单元登顶，另一个靠改变算法复杂度取胜；而同一个「常量内存」技巧在一个场景平平无奇、在另一个场景直接翻车 —— 这就是这两个 demo 放在一起讲的价值。

## 8. 复现方式

```bash
cd gpu-raytracer-demo
make            # Windows: build.bat
./raytracer_demo                                    # 默认 1024×1024, 260 球, 深度 5
./raytracer_demo --width 256 --spheres 512 --depth 4   # 规模扩展性实验
./raytracer_demo --spheres 1024                      # 触发 L4 的常量内存退回路径
./raytracer_demo --save-all                         # 各层渲染图都存为 PPM
```

算法参考：[tinyraytracer: understandable raytracing](https://github.com/ssloy/tinyraytracer/wiki/Part-1:-understandable-raytracing)（原项目为纯 CPU 版，本 demo 将其 CUDA 化并加入多层 GPU 优化与 BVH）。
